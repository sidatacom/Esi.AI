## Findings

- The loaded-model card is rendered from `loadStatus.LoadedModels`; `isOpenVinoModelLoaded` is assigned during initialization and after load, but is not used by the card.
- The OpenVINO button calls `IDataService.LoadModelAsync(OpenVinoLoadRequest)`, which invokes the `LoadOpenVinoModel` SignalR hub method. `DataHub` delegates to `DataService`, which awaits `ModelRuntime.LoadAsync` and returns a success/failure DTO.
- The page polls `GetOpenVinoModelStatus` while the load invocation is pending. Only after a successful result does it refresh the shared `loadStatus`, so a native hang/abort before the invocation returns leaves the card empty by design.
- `OpenVinoModelLoader` appends native `OvLogger` messages and commits `loadedModelPath`/pipeline state only after `LLMPipeline` or `VLMPipeline` construction and generation configuration. A log ending at native Core creation therefore indicates that model activation did not complete, or that the process terminated before the SignalR result.
- After a debug restart, `BackendRequirementMonitor` can run `OpenVinoDiagnosticsService.Diagnose()` at the same time as page initialization and a user load. The diagnostic path creates a native `OpenVinoSharp.Core`; no shared lock coordinates it with `GenAI.Initialize`/pipeline loading, and the logger callback is process-wide. This is the strongest restart-specific explanation for an intermittent Core-only log.
- History records both prior native process exits (`134`/`139`) and later successful native loads, so the repository evidence favors an intermittent/in-process native initialization or driver failure over a contract-routing defect.
- Focused tests cover deterministic validation and opt-in native load/generation, but there is no test for concurrent diagnostics plus load, the SignalR long-running invocation, or the Blazor card refresh.
