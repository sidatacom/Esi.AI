## Contract Audit

The current implementation is not a complete 99% implementation of either contract. The focused metrics change is only a partial slice and remains subject to the broader contract work below.

### Confirmed implemented

- `GET /v1/models` with loaded-model discovery and custom capability metadata.
- `POST /v1/chat/completions` in streaming and non-streaming modes.
- SSE framing, `[DONE]`, cancellation propagation, model selection, and basic error handling.
- Provider registration, model refresh, text streaming, thinking-block filtering, tool-call response assembly, token-count callback, request tracing, and API-key handling.
- OpenVINO generation already produces measured completion-token count and tokens/second.

### Confirmed gaps

- The local API accepts `tools` and `tool_choice` only through extension data and the local controller ignores them; no model-generated tool-call contract is implemented end to end.
- Incoming assistant tool history is flattened to text before local generation, so tool-call IDs and structured tool history are lost on local backends.
- Completion responses do not yet expose complete OpenAI usage accounting; prompt tokens are not measured, and the current metrics addition only contains completion tokens and throughput.
- The local API always emits `finish_reason: stop`; length and tool-call completion paths are not represented.
- OpenAI request controls such as token limits, sampling, stop sequences, response format, seed, and penalties are not modeled or applied by the local controller. Unknown fields are forwarded only by the OmniRoute path.
- Message content is string-only locally; VS Code `LanguageModelDataPart`/image input is not converted into an OpenAI multimodal content array or OpenVINO vision input.
- Provider model limits are hardcoded and provider capabilities only map image input and tool calling; no native usage response part exists in the stable VS Code provider API.
- Controller streaming, non-streaming, error, cancellation, and provider behavior lack focused automated coverage; there is no provider test suite yet.

## 99% Implementation Plan

1. Define the supported compatibility scope and a capability matrix per backend. Do not advertise a capability from model metadata unless the selected backend can execute it.
2. Complete transport DTOs in `Esi.AI.Models`: explicit chat request parameters, tool definitions/tool choice, content parts, usage, finish reasons, and OpenAI error fields. Preserve unknown fields only where forwarding is intentional.
3. Add an application-level generation options/result contract. Thread supported options through OpenVINO, Llama, Python, and dotLLM; reject unsupported options explicitly or document deterministic fallback behavior.
4. Add model-specific token counting. Use the selected OpenVINO tokenizer for prompt and completion accounting where available; keep provider token counting consistent with the backend and label any fallback as an estimate.
5. Implement local tool-call generation as a real contract only if the selected runtime can produce structured tool calls. Otherwise return a truthful unsupported-capability error and keep VS Code tool calling disabled for that model.
6. Implement multimodal input only for runtimes with an actual image pipeline. Do not silently turn image content into empty text; reject it with a structured error when OpenVINO model support is absent.
7. Make SSE completion standards-compliant: role/content/tool-call deltas, correct finish reason, final usage chunk when requested, stable error event behavior, and cancellation cleanup.
8. Make the provider contract-complete: preserve all supported message parts, map only truthful capabilities and limits, assemble tool calls by index safely, parse usage, and display measured OpenVINO metrics without polluting model history where VS Code permits.
9. Add backend contract tests, SSE parsing tests, provider tests, and live OpenVINO smoke tests for both stream modes, usage, cancellation, unsupported capabilities, and tool/image paths.
10. Bump the provider patch version, regenerate lockfile/bundle/VSIX, install the new VSIX, reload VS Code, and validate `/v1/models`, exact JSON responses, SSE output, provider registration, and a real OpenVINO chat.

## Scope Boundary

OpenAI-compatible means compatibility with the implemented endpoint subset; it does not mean implementing every OpenAI product endpoint. Credits are not available for a local OpenVINO model without a billing/pricing/accounting domain, so the truthful first milestone is measured prompt/completion usage and throughput, not credits.
