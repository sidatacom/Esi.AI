# Session log

## User request

Implement a genuinely robust and controlled way to supervise Esi.AI Studio backend processes and cleanly terminate them when they become uncontrolled. Preserve the mandatory VS Code launch path and do not start the heavy OpenVINO Qwen model automatically.

## Local hypothesis and discriminating check

Hypothesis: the current watchdog cannot reliably clean up backend processes because it is not the owner of the Studio process and only discovers one port owner. A supervisor that owns Studio, records validated PID start identities, and places the complete process tree in a dedicated process group can make userspace cleanup deterministic.

Cheap check: run the supervisor shell syntax check and an isolated start/stop lifecycle with a harmless fixture process, then verify the recorded PID identity and that no fixture descendant remains.

## Summary

Implemented and validated.

The watchdog now uses atomic key-value state with PID start-time identity, discovers only the expected Studio command, requires `ss` and `curl`, checks `/v1/models`, prevents duplicate instances, and terminates the Studio process group with bounded TERM/KILL escalation. Studio creates its own Linux process group, configures `PR_SET_PDEATHSIG`, and runs a lease monitor that stops the host when the watchdog disappears. Existing VS Code tasks and the `Esi.AI Studio (Server Debug)` launch configuration continue to provide the required entry point.

Validation completed:

- `bash -n .vscode/studio-watchdog.sh` passed.
- Isolated Studio-like process-group start/stop fixture passed.
- Real VS Code debug start passed; Studio used its own PGID and `/v1/models` returned successfully.
- Real controlled debug shutdown removed the Studio listener, watchdog state, and backend process patterns.
- Intentional watchdog `SIGKILL` caused the Studio lease monitor to close port `7010`; the subsequent debug cleanup removed the stale state.
- Studio build passed and diagnostics were clear for all new C# files.
- Existing Studio tests passed: 39 passed, 0 failed.

Residual limitation: no userspace supervisor can guarantee recovery from a kernel or Intel GPU driver lockup. In that case the OS/kernel requires its own driver, kernel, or hardware-level recovery mechanism. The implemented boundary makes userspace process ownership and cleanup deterministic when the kernel remains responsive.
