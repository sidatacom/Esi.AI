## 20260907-000747.md

<!-- BEGIN SOURCE: docs/history/20260907-000747.md -->

# Session

## User request
After reducing the context window, model loading through the UI now fails with TaskCanceledException. Investigate whether the queue change broke UI loading and restore the direct UI load path.

## Action plan
- [x] Inspect current single-flight changes and UI load call path.
- [x] Identify whether cancellation is from the shared task or native load.
- [x] Apply the smallest root-cause fix.
- [x] Validate with diagnostics and build.

## Findings
- The UI OpenVINO load calls `DataHub.LoadOpenVinoModel`, which deliberately invokes `DataService.LoadModelAsync` with `CancellationToken.None`.
- The server reported the model as `isLoading: true` while the UI showed `TaskCanceledException`; the native load continued server-side.
- A subsequent status read reported `isModelLoaded: true`, backend `OpenVINO`, device `GPU.1`, `isLoading: false`, and approximately 15 GB allocated.
- No code change was required in this session; the queue and direct UI load path are intact.

## Validation
- `GET /v1/application/models` confirmed the completed OpenVINO load.
- Existing Studio build had already passed after the queue and diagnostic changes.

## Summary

The UI cancellation was a client/SignalR wait cancellation while the server-owned OpenVINO load continued. The model is now loaded successfully; do not start a second load while the status reports `isLoading: true`. Review this summary and remove this session log from `docs/history/` after confirmation.

## Follow-up

- Added `CancelOpenVinoLoadAsync` to the data-service contract, SignalR client, hub, and server service.
- Added a `Cancel loading` button to the OpenVINO backend page.
- The cancellation token is honored at OpenVINO load synchronization boundaries. Native OpenVINO pipeline constructors do not accept a cancellation token, so cancellation takes effect when the current native constructor returns; force-disposing it mid-call was intentionally avoided.
- Studio build passed after the change.

- No active Esi.AI.Studio process found during inspection.
- The model is not loaded three times. Two Core instances are diagnostic calls; the third is the VRAM property query after pipeline creation.
- The `ArgumentException` is likely raised by an unsupported `GPU_MEMORY_STATISTICS` property and is caught by the VRAM diagnostic path.

Summary:
- Repeated Core logs indicate repeated lightweight OpenVINO Core handles, not repeated model pipeline loads.
- The diagnostic Core is created by `OpenVinoDiagnosticsService.Diagnose`; the post-load Core is created by `OpenVinoModelLoader.TryGetVramUsageMiB`.

- Validation: OpenVINO loader tests passed 20/20 and the Studio build succeeded.
- VRAM follow-up: the loader now keeps one reusable metrics Core, tries the requested device and the generic `GPU` alias, and disposes it with the loader. It no longer constructs a Core for every load/statistics query.
- Validation: OpenVINO loader tests passed 20/20, compiler diagnostics reported no errors, and the Studio build succeeded.
- Root-cause API review: the installed `libopenvino_genai_c.so` exports only `ov_genai_llm_pipeline_create` and `ov_genai_vlm_pipeline_create`; neither accepts an existing `ov_core_t`. The workspace contains only the C# binding, not the native GenAI implementation, so a real shared-Core fix requires a native OpenVINO GenAI build/API extension.
- DI follow-up: `ModelRuntime` was previously created through its parameterless constructor and internally created a second `OpenVinoModelLoader` and a second `OpenVinoLoadGate`. Studio now constructs it explicitly with the registered loader and gate, so diagnostics, VRAM metrics, and runtime loading share the intended DI objects.
- Validation: `Program.cs` has no diagnostics and the Studio build succeeded.

## 20260907-092059.md

# Sitzungsnotiz

## Anfrage
Die Maschine friert erneut vollständig ein. Es soll ein besserer Schutz mit einem Kernel-Watchdog installiert werden.

## Befund
- Ubuntu 26.04.1 LTS, Kernel 7.0.0-31-generic, physischer Intel-Z390-Host.
- Kein `/dev/watchdog` und keine aktive systemd-Watchdog-Konfiguration.
- `iTCO_wdt` und `softdog` sind im Kernel verfügbar; für diesen Host ist `iTCO_wdt` die bevorzugte Variante.
- `kernel.watchdog=1`, `kernel.nmi_watchdog=1`, aber `kernel.softlockup_panic=0`, `kernel.hardlockup_panic=0`, `kernel.panic=0`.
- Vorherige Bootmeldungen zeigen gleichzeitig aktive NVIDIA-, i915- und xe-Grafiktreiber.
- Installation konnte nicht automatisch erfolgen, weil `sudo -n` keine passwortlose Authentifizierung erlaubt.

## Aktionsplan
- [x] Watchdog-Hardware und Kernelmodule read-only prüfen.
- [x] systemd- und Kernel-Watchdog-Zustand prüfen.
- [x] Freeze-Hinweise aus vorherigem Boot prüfen.
- [ ] Intel-Hardware-Watchdog durch den Benutzer mit Root-Rechten laden und dauerhaft aktivieren.
- [ ] systemd Runtime- und Reboot-Watchdog konfigurieren.
- [ ] sysctl-Panic-Recovery konfigurieren und bewusst validieren.
- [ ] Nach Neustart Gerät, systemd-Werte und Bootstatus prüfen.

## Zusammenfassung
Die eigentliche Schutzschicht gehört auf Kernel/systemd-Ebene, nicht in Esi.AI. Die benötigten Befehle werden nach der Sitzung als geprüfter Root-Block ausgegeben. Die Aktivierung eines Watchdogs kann bei Fehlkonfiguration einen Neustart auslösen; deshalb wird kein riskanter Test-Hänger automatisiert erzeugt.
