## Findings
- LocalAI accepts structured OpenAI-compatible `tools` and `tool_choice`.
- The request path serializes these as backend `PredictOptions.Tools` and `ToolChoice` JSON strings.
- With `use_tokenizer_template`, Python backends such as vLLM and SGLang call the tokenizer's `apply_chat_template(..., tools=...)` and use a backend/model-specific tool parser.
- With legacy Go templates, LocalAI renders functions into its own prompt template and may use grammar generation plus output parsers.
- A configured `system_prompt` is a separate instruction message and is not the canonical tool interface. LocalAI may prepend it when no system message exists.
- Therefore the model's chat/Jinja template is authoritative when the backend supports structured tool templates; a system-prompt/tool-text fallback is backend/model-specific compatibility behavior.

## Summary
- LocalAI has a clear structured boundary: OpenAI `tools` and `tool_choice` enter as request data, are normalized by LocalAI, and are forwarded to the selected backend.
- For tokenizer-template models, the backend applies the model's Jinja chat template with `tools=...`; the output parser converts generated tool markup into structured tool calls.
- For legacy models, LocalAI's own prompt template plus grammar/parser configuration is the compatibility path.
- Esi.AI should keep the structured tool contract and let each backend choose its native template/parser or explicitly reject unsupported tools. It should not use a universal system-prompt injection.
