- Die geaenderten Dateien sind diagnostikfrei; der Studio-Build war erfolgreich.
- Die direkte API-Pruefung zeigte fuer `apps` keine belastbare dokumentierte Mehrfachsemantik; Esi.AI erzwingt deshalb OR durch separate App-Abfragen und dedupliziertes Zusammenfuehren.

## 20260903-110517.md

<!-- BEGIN SOURCE: docs/history/20260903-110517.md -->

# Session

User request:
Gibt es ein Qwen3.8-Modell aus den Hugging-Face-Ergebnissen, das auf eine Intel B70 mit 32 GB VRAM passt?

## Action plan

- [x] Relevante Qwen3.8-Modellvarianten und Quantisierungen ermitteln.
- [x] Dateigrößen und Modelltypen gegen 32 GB VRAM vergleichen.
- [x] SGLang-Unterstützung für Intel XPU und die B-Series prüfen.
- [x] Eine konkrete Empfehlung für die Intel B70 formulieren.

Dependencies/prerequisites: Zugriff auf aktuelle Hugging-Face- und SGLang-Dokumentation; Runtime ist SGLang; Zielhardware ist Intel B70 mit 32 GB VRAM.

## Findings

- Qwen3.8-27B ist der relevante Kandidat. BF16 benötigt ungefähr 54 GB für die Gewichte und passt daher nicht in 32 GB. Die dokumentierte FP8-Variante liegt bei ungefähr 28,5 GB vor zusätzlichem Runtime-, KV-Cache- und Framework-Speicher.
- Die offizielle SGLang-Rezeptseite für Qwen3.8-27B dokumentiert BF16, FP8 und NVFP4, validiert diese Rezepte jedoch auf H200, RTX PRO 6000, RTX 5090, DGX Spark und GB300, nicht auf Intel XPU.
- SGLang besitzt einen experimentellen Intel-XPU-Backendpfad. Die aktuelle XPU-Dokumentation nennt Intel Arc Pro B-Series und Arc B-Series als Zielplattformen und verlangt eine Installation aus dem Quellcode. Der Startpfad verwendet `--device xpu`, `--attention-backend intel_xpu` und eine Seitengröße von 32, 64 oder 128.
- Die optimierte Intel-XPU-Modellliste enthält Llama-3.1/3.2 und Qwen2.5-1.5B, nicht Qwen3.8-27B. Als auf XPU getestete Prefill/Decode-Modelle werden Qwen3-0.6B und Qwen2.5-7B genannt. Damit ist Qwen3.8-27B auf Intel B70 nicht als SGLang-Modell validiert.
- Die aktuelle SGLang-Quantisierungstabelle führt Plattformunterstützung für NVIDIA, AMD und Ascend auf, aber keine Intel-XPU-Unterstützung für die Qwen3.8-relevanten FP8/NVFP4/GGUF-Pfade. GGUF wird dort mit CUDA-Kernels beschrieben. Intel AutoRound ist dokumentiert, aber der GPU-Pfad für Qwen3.8-27B ist dadurch nicht belegt.
- Zusätzlich ist speculative decoding im Intel-XPU-Pfad laut Dokumentation noch nicht implementiert.

## Conclusion

Qwen3.8-27B passt auf die Intel B70 nur theoretisch als stark quantisierte Gewichtsdatei. Für **SGLang auf Intel B70** gibt es aktuell keine ausreichende offizielle Modell-, Quantisierungs- oder Laufzeitvalidierung, daher ist keine Qwen3.8-Variante belastbar empfehlbar. Eine FP8-Datei sollte nicht allein wegen ihrer Größe als funktionierend angenommen werden.

Für einen belastbaren B70-Test wäre der kleinste sinnvolle Versuch eine aktuelle SGLang-XPU-Source-Installation mit einem normalen Qwen3.8-27B-Checkpoint, `--device xpu`, `--attention-backend intel_xpu` und ohne speculative decoding. Das wäre ein Experiment, keine dokumentierte Rezeptur. Für eine verlässlichere Intel-Ausführung sind OpenVINO oder llama.cpp mit einem dafür unterstützten Format die naheliegenderen Alternativen.

## Verification status

- Keine Modelldateien heruntergeladen.
- Kein SGLang-Server gestartet.
- Keine reale VRAM- oder B70-Kompatibilitätsmessung durchgeführt.
- Recherche abgeschlossen am 2026-09-03; die Aussage bezieht sich auf die zu diesem Zeitpunkt aktuelle SGLang-Dokumentation und den aktuellen Repositorystand.

# Session

User request: Der Chat im OpenVINO-Backend über die WebAPI funktioniert nicht mehr.

## Action plan

- [x] Identify the WebAPI request path from the browser page through the OpenAI-compatible controller to the OpenVINO runtime.
- [x] Reproduce the failure with the smallest available request and capture the HTTP status and server-side error.
- [ ] Apply the smallest root-cause fix within the owning layer, preserving the existing API and SignalR architecture.
- [ ] Add or update a focused regression test for the failed behavior.
- [ ] Validate the changed slice, rebuild/restart the monitored Studio session as required, and record the result.

## Working hypothesis

The OpenVINO WebAPI chat failure is likely caused by a request-contract or runtime mapping regression rather than a compile-time problem. The discriminating check is a minimal chat request against the running OpenAI-compatible endpoint and its server response/log.

## Provider log findings

- The relevant tool-optimizer activity occurred on 2026-09-03 between 11:39:17Z and 11:39:48Z.
- Four parallel `POST /v1/chat/completions` requests were accepted with HTTP 200 and `text/event-stream` responses. Their requests used `max_tokens: 65536`, `stream: true`, and `tools: []`.
- Two streams emitted only the initial assistant role chunk. Two emitted text chunks and reached the provider's bounded trace message, but none of the four streams emitted `[DONE]`.
- The seven `[DONE]` markers in the file belong to the older 2026-09-02 run and do not validate the stuck interaction.
- After the four POSTs, the provider repeatedly queried `GET /v1/models` approximately every five seconds. The later log contains no further chat POST for the stuck interaction.
- `OpenVinoModelLoader` already serializes generation through `generationLock`. `OpenAiCompatibleController` does not emit `[DONE]` until native generation returns, so a long or non-terminating OpenVINO generation leaves the SSE request open.
- The provider's `requestTimeoutMs` timer is cleared as soon as `fetch` receives response headers; it does not time out an SSE body read. This is a separate provider robustness issue and was not changed in this diagnostic pass.

## Diagnostic conclusion

The log proves an incomplete SSE lifecycle for the tool-optimizer requests, not an HTTP connectivity failure. The strongest immediate suspect is the configured `max_tokens: 65536` combined with four parallel optimizer requests and serialized OpenVINO generation. No source code or packaged provider files were changed in this pass; a repair should first reproduce with a fresh log and a bounded optimizer request, then separately add stream-read cancellation handling if the backend completes without `[DONE]`.

- [complete] Review OpenAI-compatible Chat Completions streaming and SSE keep-alive guidance.

## Findings

- VS Code's LanguageModelChatProvider contract requires response parts through the progress callback and supports cancellation; it defines no heartbeat event.
- OpenAI Chat Completions streaming is a sequence of SSE chat completion chunks, followed by `data: [DONE]`; the reference does not require heartbeat frames.
- WHATWG SSE explicitly permits colon-prefixed comment lines and recommends sending them about every 15 seconds to protect long-lived connections from legacy proxies.
- The Studio heartbeat is therefore valid transport-level hardening and should be ignored by the provider parser. It can help only when an intermediary drops an otherwise healthy idle connection.
- It cannot repair a hung native generation, stale Studio process, cancellation, or a server-side connection failure. Those remain the primary investigation targets.

## Summary

Documentation supports retaining the heartbeat as an optional keep-alive, while treating it as unrelated to the OpenAI semantic contract and VS Code tool-call contract. A real long-running Agent request should be used to prove whether an intermediary idle timeout exists before calling the heartbeat a fix.
