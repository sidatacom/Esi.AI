### Confirmed gaps

- Incoming assistant tool history is flattened to text before local generation, so tool-call IDs and structured tool history are lost on local backends.

- Message content is string-only locally; VS Code `LanguageModelDataPart`/image input is not converted into an OpenAI multimodal content array or OpenVINO vision input.

3. Add an application-level generation options/result contract. Thread supported options through OpenVINO, Llama, Python, and dotLLM; reject unsupported options explicitly or document deterministic fallback behavior.
4. Add model-specific token counting. Use the selected OpenVINO tokenizer for prompt and completion accounting where available; keep provider token counting consistent with the backend and label any fallback as an estimate.
5. Implement local tool-call generation as a real contract only if the selected runtime can produce structured tool calls. Otherwise return a truthful unsupported-capability error and keep VS Code tool calling disabled for that model.
6. Implement multimodal input only for runtimes with an actual image pipeline. Do not silently turn image content into empty text; reject it with a structured error when OpenVINO model support is absent.
7. Make SSE completion standards-compliant: role/content/tool-call deltas, correct finish reason, final usage chunk when requested, stable error event behavior, and cancellation cleanup.
8. Make the provider contract-complete: preserve all supported message parts, map only truthful capabilities and limits, assemble tool calls by index safely, parse usage, and display measured OpenVINO metrics without polluting model history where VS Code permits.
