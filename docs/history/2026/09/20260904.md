# Session History

## User Request
Beim Bild-Request wurde ein falscher Bildinhalt beschrieben. Der Nutzer fragt, wie die Bilddaten in Tokens umgewandelt werden oder ob sie binär an das Modell gesendet werden.

## Diagnosis
Das angehängte Bild zeigt vier Logos: Ollama, llama.cpp, vLLM und LM Studio.

Der Provider sendet Bilddaten als lokale `data:image/...;base64,...`-Data-URL in einem OpenAI-Content-Array. Der Studio-Controller dekodiert die Base64-Daten zu Bytes. Für OpenVINO werden die Bytes mit ImageSharp in RGB-Pixel und anschließend in einen RGB-NHWC-U8-Tensor umgewandelt. Dieser Tensor wird an `VLMPipeline.GenerateWithHistory` übergeben. OpenVINO führt die Bildvorverarbeitung, den Vision Encoder und die interne Bildrepräsentation selbst aus; Studio erzeugt keine Bildtokens manuell.

Für Llama werden die dekodierten Bytes an LLamaSharp MTMD übergeben; auch dort übernimmt die native Runtime die Vision-Verarbeitung.

## Result
Die vorherige Antwort war inhaltlich falsch und vermutlich eine Modellfehlinterpretation. Das Bild wird nicht als vom Studio erzeugte Tokenfolge verschickt, sondern als Base64 im HTTP-Request transportiert und serverseitig als Bildtensor an OpenVINO übergeben. Die lokale-only Einschränkung bleibt bestehen; Remote-Bild-URLs werden nicht geladen.

## Follow-up Test
Auf Wunsch wurde in `src/Esi.AI/Esi.AI.Studio.Tests/OpenAiCompatibleControllerTests.cs` ein Test ergänzt, der einen OpenAI-kompatiblen Chat mit Text und lokaler Base64-BMP simuliert. Der Test prüft Parsing, Bilddekodierung, RGB-NHWC-U8-Tensorform und Pixelreihenfolge.

Validierung: der neue Test `1/1` und die vollständige Controller-Testklasse `17/17` bestanden. Die Studio-Debugsession und der Watchdog wurden anschließend beendet.
