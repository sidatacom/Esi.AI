# Findings

- `GetProcessSchemeWithParametersAsync` throws when its filtered query finds no row in `WorkflowProcessScheme` for the requested code. Its filters also include obsolete status, root scheme ID, and tenant ID.
- `OptimajetFlowRuntime.ExecuteRouteAsync` saves XML through `SaveSchemeAsync(string, ...)`, then immediately calls `WorkflowRuntime.CreateInstanceAsync`. In the SQLite provider, this overload upserts the raw scheme into `WorkflowScheme`; the process-scheme lookup reads `WorkflowProcessScheme`. The thrown exception confirms no usable process-scheme row existed when creation reached that lookup.
- The reported code is deterministic from the flow definition ID, version, and route target. A different persisted definition/version/route target, or a different relative SQLite database selected by the Studio working directory, can therefore leave the queried process-scheme row absent.
- No source changes were made. A Studio test/build was not run: the required preflight found an active VS Code debug session and a `dotnet` process listening on port 7010, so the Studio Build Gate did not permit running it.

# Summary

The exception is a persistence/lookup mismatch, not a malformed process ID: at creation time the SQLite provider cannot find the compiled process-scheme record under the exact computed code and scope filters. Verify the runtime's effective `DefaultConnection` database and inspect both `WorkflowScheme` and `WorkflowProcessScheme` for the exact code before changing data. Do not delete or migrate database rows blindly.
