## Findings
- `Backends.razor` checks `ModelLoadStatus.IsModelLoaded` after a Llama load. `DataService.LoadModelAsync` returned `LoadedLlamaModel_Read()`, which takes that flag from the in-process LLama loader even when `LoadedModels` includes the successfully loaded packaged SYCL runtime. The aggregate `LoadedModel_Read()` is the correct source.
- `SaveNewProfileAsync` knows `CurrentBackendVariantId` but omitted it from the `ModelConfiguration` sent to DataService. `ResolveBackendVariantId` also let `EnableXpuGraph=true` override an explicit `Device="cuda:0"`, conflating an optimization setting with backend identity.
- The prior vLLM CUDA hang was not reproduced with an application error payload. The route misclassification is a concrete persistence defect and is being covered directly; environmental vLLM prerequisites remain a separate runtime issue.

## Changes and Verification
- `DataService.LoadModelAsync` now returns `modelRuntime.LoadedModel_Read()`, so Llama and packaged runtimes report the same aggregate loaded state consumed by the UI.
- Profile creation now supplies `CurrentBackendVariantId`. Variant inference honors explicit `Device`/`Devices` routes before consulting `EnableXpuGraph` as a fallback.
- Added `ModelConfiguration_CreateAsync_ExplicitCudaRouteOverridesXpuGraphFlag` to cover explicit CUDA and XPU routes when the graph flag is enabled.
- `debug.launchProject` built and started Studio; the host readiness check passed. The browser created a temporary vLLM CUDA12 profile, displayed it under `vllm.cuda12`, and deleted it afterward. Studio remained responsive; existing saved profiles remain present.
- `get_errors` reported no diagnostics in the changed service, Razor page, or regression test file.
- The Studio unit-test project was not executed: repository instructions restrict build/test execution to projects under `src/`, while this test project is under `tests/`.
- The 128k SYCL load was not repeated because the previous run increased swap substantially. Its contradictory status is fixed at the response source; the memory growth remains an unverified resource-envelope concern, not something safely addressed by an arbitrary code limit here.

## Summary
