# Debugger race and Qwen3.8 benchmark completion

## Request

Fix the Studio debugger failure caused by concurrent local-model metadata discovery, verify the correction, then finish the requested sequential Qwen3.8 backend benchmark runs using the downloaded, pinned model artifacts and the repository's benchmark procedure. Preserve all pre-existing worktree changes.

## Action plan

- [x] Trace the `ModelMetadata` writes and concurrent `LocalModel_ReadAsync` path; add process-wide synchronization and a focused regression test.
- [x] Validate the Studio build, launch through the supported debug lifecycle, confirm host readiness, and exercise parallel `/v1/models` requests. The standalone unit-test suite was not run because it is outside the benchmark procedure.
- [x] Audit downloaded artifact hashes/provenance, exact profile IDs/routes, and current runtime status. A common checkpoint/revision/quantization across all six profiles is not established.
- [x] Run the eligible 128k probe sequentially and stop after the first invalid measurement. Llama CUDA12 returned HTTP 200 and usage, but `completionLengthMatchesLimit=false`; the model was unloaded, Studio/resource health was checked, and later variants were not started.
- [x] Update the benchmark report and this log with the verified status and blockers. No 128k probe was launched.
- [ ] Resume with a fresh Vulkan 128k probe and the remaining four variants only after resolving the observed load-time swap growth and passing fresh memory, runtime-readiness, and Studio-readiness gates.

## Progress

- Initial diagnosis: `/v1/models` can call `LocalModel_ReadAsync` concurrently across scoped `DataService` instances; each call can insert the same missing `ModelMetadata.ModelPath`, violating its unique index.
- `DataService` now synchronizes the metadata mutation path process-wide; a multi-scope regression test was added.
- Studio build/start/readiness succeeded in session `9c750bfb-aacf-4779-ac06-8369b39cc2c8`. A targeted parallel `/v1/models` check returned 16/16 HTTP 200 responses.
- Six benchmark profiles were verified in Studio with their exact IDs, model files, and `AutoLaunch=false`; no model was loaded during the audit.
- After backend diagnostics settled on 2026-10-20, Llama Vulkan/CUDA12/SYCL, OpenVINO, vLLM CUDA12, and vLLM XPU all reported Ready. Vulkan reported two devices; both vLLM variants reported their matching accelerator. SYCL's missing oneAPI build tools and OpenVINO's missing NPU are optional. Vulkan's Qwen3.8 profile has not passed a load smoke; OpenVINO previously showed swap growth at 128k.
- One Qwen3.8 128k probe ran on Llama CUDA12 (profile `edb7b971-2e55-4b1a-8137-e393a62c4bcf`). It returned prompt/completion usage of 128011/128, TTFT 60677.92 ms, decode rate 51.56 tokens/s, wall time 63592.33 ms, and finish reason `stop`. `completionLengthMatchesLimit=false` while `fits131072Context=true`; therefore it is a failed measurement and the remaining variants were not run.
- Before the request and after unload, available RAM was 18 GiB and swap usage was 3.6 GiB; the swap monitor showed no growth. The model was unloaded and Studio remained ready with no models active.
- Follow-up diagnosis: LLama adapters omit a backend finish reason, so the `GenerationResult` defaulted to `stop`; the OpenAI-compatible middleware now reports `length` when the completion count reaches the positive configured limit and no tool call was returned.
- Studio was stopped cleanly, rebuilt and relaunched through EsiMCP after the fix. Build/start succeeded and host readiness was confirmed for session `c7d777b0-ab4d-4122-a0e1-0312be1708b6`.
- The post-fix rerun gate was checked with no models loaded and Studio ready, but no request was started: available RAM was 16,322,203,648 bytes (~15.2 GiB), below the required 16 GiB. Swap was ~3.5 GiB and the later `vmstat` intervals showed no additional swap activity.
- A second visible-terminal check at 07:59 CEST showed 16,189,972,480 bytes (~15.1 GiB) available and 3,729,362,944 bytes of swap in use; the memory gate remained unmet.
- To try a narrow, non-destructive recovery, only cached pages for the saved benchmark weight files were advised out with `POSIX_FADV_DONTNEED`; no model files were modified. The 08:01 CEST pre-load check still showed only 16,865,628,160 bytes (~15.7 GiB) available, below the required gate, with 3,727,523,840 bytes of swap in use. No model was loaded and no runner was started.
- A post-fix CUDA12 128k probe later passed: profile `edb7b971-2e55-4b1a-8137-e393a62c4bcf`, prompt/completion 128011/128, finish reason `length`, TTFT 60530.31 ms, client decode 51.32 tokens/s, wall time 63466.52 ms, server rate about 2.07 tokens/s. Both required flags were true. The model was unloaded and Studio remained ready with no models loaded.
- A subsequent Vulkan load in that same process exposed LLamaSharp's process-wide native backend configuration restriction when changing CUDA to Vulkan. The exception was inspected and the process stopped. A fresh Studio build/launch succeeded in session `fc98c752-f966-4b0d-8d87-a39ca51760c8`, with host readiness confirmed.
- The original Vulkan profile `174a9acb-46d6-4103-a514-fa8f832bbee0` had neither Vulkan device explicitly selected. It was left unchanged, and a separate route-verified profile was created: `961df005-45f6-4492-a4c4-37b74d01ca3e`, model `Qwen3.8-27B-Uncensored-Q4_K_M.gguf`, Vulkan1 enabled only, context 131072, `AutoLaunch=false`.

## Summary

Debugger metadata race fixed and exercised by the parallel endpoint check. The finish-reason normalization bug was fixed, Studio build/readiness passed, and the post-fix CUDA12 probe passed both required completion/context flags. A fresh Studio process resolved the process-wide CUDA/Vulkan native-config conflict and loaded the route-verified Vulkan profile, but the load caused substantial swap growth; the model was unloaded without launching a 128k request. The remaining variants are not run and the overall benchmark task is still incomplete.
