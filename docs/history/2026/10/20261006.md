## Findings

- The repeat's SSE timestamps convert to 2026-10-06 19:18:26 and 19:18:42 CEST. The kernel journal query from 19:00 through the end of that date returned no matching Xe errors, so the earlier 119,052 `-105` fault is not evidence for this repeat.

The 2:17 interruption was well before that deadline and therefore was not a timeout failure.
- Confirmed cancellation defect: `OpenVinoChatSession.Generate` passes callbacks to both `LLMPipeline` and `VLMPipeline` that always return `StreamingStatus.Running`. The binding exposes `StreamingStatus.Cancel`, but the request cancellation token is not passed to this session. Thus cancellation during callback-driven generation is ignored.
- The observed stall occurred before any generated token, so the callback defect alone does not explain the long prefill. The synchronous native `GenerateWithHistory` call can continue running after the HTTP request is canceled; cleanup waits for that task before releasing the generation lock. This matches Studio continuing to consume CPU after the client was interrupted.
- The controller is designed to emit SSE heartbeats every 15 seconds while waiting, but the captured repeat had only one null-content frame after the initial role frame. The available capture does not explain why further heartbeats stopped.

## Conclusion

A code-level cancellation bug is confirmed and can leave native inference and its generation lock active after the client gives up. The underlying reason the 118k prefill stalled is not established: no matching Xe fault or native exception was captured for that repeat. The earlier 119,052 `ENOBUFS` failure remains adjacent evidence, not proof of this run's cause. Further root-cause attribution needs instrumentation around native call entry/exit, cancellation, and each SSE heartbeat during a controlled repeat.
