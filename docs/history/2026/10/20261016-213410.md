## Summary

Implemented the persisted inference log and the live `/inference-logs` Studio page. The page displays request correlation ID, path, backend/model, approximate prefill tokens, message/image/tool counts, streaming, duration, outcome, and error detail; chat/image/tool payloads are not stored. SQLite retains the latest 500 completed entries and marks entries left running after a process restart as interrupted.

Validation: Studio build succeeded with 17 existing NuGet vulnerability warnings. The migration applied at startup and the page loaded successfully at `http://localhost:7010/inference-logs`; an initial SQLite `DateTimeOffset` ordering error was corrected by sorting the bounded result set in memory. The final retention change was rebuilt through the EsiMCP lifecycle after the previous watch host stopped responding. The new debug session reported ready, and reloading `/inference-logs` showed the empty-state message without the SQLite error. No model inference was sent during validation.

## Follow-up: OpenVINO CCS failure at 21:57

The Web API log correlated request `req-368260405f694ca88759c01fc04a4888` with an OpenVINO VLM inference starting at 21:57:40. Metadata showed 2 messages, 0 images, 0 tools, and an estimated prefill size of 105,134 tokens; no payload was stored. At 21:57:45, the Linux `xe` kernel driver reported CCS memory faults with unsuccessful `-ENOENT` responses, repeated engine memory CAT error 18 messages, and a CCS engine reset. The debugger stopped on the OpenVINO `UNKNOWN_ERROR (-17)` exception at 19:57:46Z.

Resuming the debugger let the configured fatal-failure path stop Studio. The SQLite row remained `Running` until the next startup marked it `Interrupted`, revealing that shutdown began before the outer request handler could persist its failure result. The OpenAI and SignalR inference paths now defer fatal coordination until after the failed log update; the coordinator unloads runtimes before requesting host shutdown. The Studio project rebuilt and relaunched successfully, and the log page loaded with the prior request marked `Interrupted`. No further inference was sent, so a new `Failed` row from the updated path was not runtime-tested.

## Follow-up: repeated failure at 22:26

The next request, `req-368054fd6b2b4666b2d418cd4c2fcf31`, again used the OpenVINO model configuration `Benchmark - Qwen3.8 - OpenVINO`, path `/home/llm/models/Qwen3.8-27B-Uncensored-int4-awq-g128-ov`, and selected device `GPU.1`. It contained 2 messages, 0 images, 0 tools, and an estimated 105,134 prefill tokens. After the debugger resumed, its persisted status became `Failed` with `OpenVinoSharp.OVException` and `Unknown error (-17)`, confirming that failure logging now completes before shutdown.

Kernel messages at 22:26:41 again show repeated `xe` CCS `Engine memory CAT error [18]` events and unsuccessful `-ENOENT` fault responses at the same time as the native exception. This ties the repeatable failure to a GPU-side memory fault during inference, rather than the image path: the request log reports zero images. The model configuration reports `model_type: qwen3_5`, a 262,144-token maximum position length, and a 15,708,063,435-byte model directory. For this architecture (64 layers, 4 KV heads, head dimension 256), 105,134 tokens imply roughly 6.9 GB of KV cache even at the runtime's configured 4-bit KV precision, before execution workspaces and other runtime allocations. The existing OpenVINO path already sets `KV_CACHE_PRECISION=u4`, large GPU allocations, and the paged-attention backend for this model.

The 262,144 value is the model's sequence-length limit, not a guarantee that the selected device can hold a 105k-token prefill for this 27B model. The request evidence establishes a GPU-side failure, but not a safe prompt limit or a tested alternative route. No prompt truncation or speculative limit was introduced. The later driver investigation below provides a stronger Xe CCS allocator root-cause candidate.

## Follow-up: Xe flat-CCS allocator fix

Further host inspection identified the discrete device as Intel Battlemage G31 (`8086:e223`, PCI `03:00.0`, `xe` driver). The active kernel is `7.0.0-34-generic`; `7.0.0-38-generic` is installed but not active. Upstream Linux commit [`818bebeb63dd6bf5f4e07e145f6cdbace520a34c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=818bebeb63dd6bf5f4e07e145f6cdbace520a34c) fixes flat-CCS VRAM accounting in `xe_vram.c`: the CCS boundary is rounded down to the allocator's page size instead of up, so reserved compression storage is not exposed as usable VRAM. The commit identifies Battlemage as affected and is a strong match for the repeated CCS/CAT faults, but its described reproducer is a G21/16-GiB layout; the exact memory layout on this G31 and whether the installed Ubuntu kernel backports the fix have not been verified.

No repository-side prompt limit can correct a kernel VRAM allocator fault. The app's configured 4-bit KV cache, large-allocation setting, and paged attention were already active; a guessed cap would only reject requests without establishing a safe limit. No model was loaded and no failing request was repeated during this investigation. No kernel package or reboot operation was performed because explicit authorization for a host-level change was not available. The inference failure therefore remains unresolved until a kernel containing this fix (or a verified stable backport) is booted and the request is validated.

The configured Ubuntu 26.04 repositories currently offer `7.0.0-38.38` as the latest HWE kernel; its changelog does not identify the flat-CCS fix, so its presence is unverified. The upstream fix is included in the Ubuntu mainline `v7.3-rc3` build (verified by upstream commit ancestry), but the available amd64 image package is unsigned and is a release candidate. Secure Boot is enabled, and no local MOK signing pair is present, so booting it would require creating/enrolling a signing key and rebooting through the MOK manager. No such operation was performed.
