## Driver investigation

The request reaches `OpenVinoRuntime` on the OpenVINO `GPU.1` route. Its Qwen3.5 VLM configuration already uses 4-bit KV cache, GPU large allocations, and paged attention. The wrapper exposes prompt-token counts only after generation; adding an arbitrary token cap or using the approximate log estimate as an exact admission limit would risk rejecting valid requests without fixing a kernel allocator bug.

System evidence identifies the selected discrete device as Intel Battlemage G31 (`8086:e223`, kernel driver `xe`). The active kernel is `7.0.0-34-generic`; `7.0.0-38-generic` is installed but is not the running kernel. The upstream Linux Xe change `818bebeb63dd6bf5f4e07e145f6cdbace520a34c` fixes flat-CCS VRAM accounting by rounding the CCS boundary down rather than up, preventing reserved CCS storage from being exposed to the VRAM allocator. The failure symptoms and device family make this a strong driver-level lead, but the installed `7.0.0-38` backport status and the exact affected memory layout on this G31 have not been verified.

The Studio debug session is inactive and port 7010 is free. No model was loaded, no request was repeated, and no kernel/package/reboot operation was performed. A repository-side prefill limit would be speculative and cannot repair a kernel VRAM allocator fault; updating or booting a kernel with the Xe fix is the meaningful next step and requires approval because it changes the host and may interrupt it.

The configured Ubuntu repositories offer only `7.0.0-38.38` as the latest HWE kernel; its changelog does not identify the CCS fix. The upstream fix is included in Ubuntu's mainline `v7.3-rc3` build (verified by comparing the upstream commit ancestry), but that build is a release candidate and its amd64 image package is unsigned. Secure Boot is enabled, and the local MOK signing pair is absent, so the kernel cannot be signed/enrolled unattended; booting it requires a signing/enrollment step and a reboot.

## Outcome

The user explicitly requested installing the kernel fix, said they would reboot afterward, and stated they do not want Secure Boot. The unsigned Ubuntu mainline `v7.3-rc3` kernel image and matching modules were downloaded from the official mainline archive; `dpkg-deb --info` succeeded for both and local SHA-256 values were recorded. A published SHA-256 manifest was not available at the attempted URL. After the user entered sudo authentication locally, both packages installed successfully as `7.3.0-070300rc3.202609132247`; `dpkg --audit` reported no incomplete package configuration. The initramfs was generated and GRUB contains the new kernel entry ahead of the previously installed kernels. The initramfs generation emitted a non-fatal warning that configured `RESUME` UUID has no matching swap device. Secure Boot remained enabled and the running kernel remained `7.0.0-34-generic`; this led to the MOK signing route described below rather than disabling Secure Boot. Do not repeat the known-failing 105k-token request until a short controlled request succeeds on the patched kernel.

The user could not disable Secure Boot and authorized keeping it enabled while enrolling a local MOK. A root-only RSA-3072 signing key was generated under `/root/esi-ai-xe-mok`; the private key has mode 0600. The kernel image is now signed with that key, independently verified by `sbverify`, and the original unsigned image is backed up under `/var/backups`. Inspection found all 6,944 packaged modules already signed with the kernel build key (`CONFIG_MODULE_SIG_ALL=y`), so those modules were left unchanged. `mokutil --import` has staged the matching public certificate; `mokutil --list-new` confirms the enrollment request. Secure Boot remains enabled, and the currently running kernel is still `7.0.0-34-generic`. No reboot or inference test has been performed. The user must confirm “Enroll MOK” in MokManager on the next reboot, using the one-time enrollment password communicated in chat, then boot into the signed 7.3.0-070300rc3 kernel. The password is deliberately not stored in this history file.

## User-requested rollback

The user could not complete the pre-boot MOK enrollment and requested that the changes be undone. The pending MOK import was revoked; `mokutil --list-new` is now empty. Both `7.3.0-070300rc3` packages were removed and purged, and GRUB no longer contains that kernel. `/boot/vmlinuz` and `/boot/initrd.img` again point to the installed `7.0.0-38-generic`; the currently running kernel remains `7.0.0-34-generic`. Secure Boot remains enabled. The local signing key, unsigned-kernel backup, downloaded package files, and temporary signing files were removed. `dpkg --audit` is clean. No reboot was performed, and the OpenVINO error remains unresolved and untested.

The user has SSH access only and cannot interact with BIOS or MokManager. The currently installed `7.0.0-38-generic` image is Canonical-signed, and GRUB's default entry selects it automatically on a normal reboot. The local package changelog does not list the flat-CCS boundary fix, and the configured Ubuntu repositories have no newer signed kernel candidate. Thus an unattended SSH reboot into `7.0.0-38` is possible as a diagnostic, but the kernel fix is not confirmed there; applying the exact fix still requires a trusted signed kernel/module path.

The user clarified that they want to remain on the currently running `7.0.0-34-generic` kernel for now. Added `/etc/default/grub.d/99-kernel-default.cfg` to select that exact advanced menu entry, ran `update-grub`, and confirmed the generated config selects the requested entry and passes `grub-script-check`. No reboot was performed. The active kernel remains `7.0.0-34-generic`, Secure Boot remains enabled, and there is no pending MOK enrollment.

## Signed kernel switch and smoke test

At the user's later request, changed the GRUB default from `7.0.0-34-generic` to the installed Canonical-signed `7.0.0-38-generic`, regenerated the GRUB configuration, and checked the selected menu ID and `grub-script-check`. Verified the `7.0.0-38` image signature with Canonical's Secure Boot signing certificate, then initiated a normal reboot over SSH. After reconnect, `uname -r` reported `7.0.0-38-generic`, `mokutil --sb-state` reported Secure Boot enabled, and systemd reported the system running.

Restarted Esi.AI Studio through `debug.launchProject`; the debug session became active and host readiness passed. The OpenVINO backend reports the Intel Battlemage dGPU and `xe` route available. Loaded the user's saved `Benchmark - Qwen3.8 - OpenVINO` configuration for `Qwen3.8-27B-Uncensored-int4-awq-g128-ov` on `GPU.1`. A new chat smoke test asked the model to return `OPENVINO_KERNEL_TEST_OK`; OpenVINO returned that exact response in 33 generated tokens (TTFT 564 ms, prefill 1.8 s, decode 1.5 s). This proves basic inference works on the signed `7.0.0-38` kernel with Secure Boot enabled.

At the user's request, reproduced the large-prefill workload over the OpenAI-compatible `/v1/chat/completions` endpoint on that same model/configuration/device. The request contained one text message with approximately 105k tokens and capped generation at 8 tokens. Studio's inference log estimated 105,030 input tokens; OpenVINO reported 105,051 prompt tokens. It returned HTTP 200 and completed in 80.7 seconds (prefill 80.6 seconds), generating 8 tokens; the short output was not semantically evaluated. The kernel message watcher captured no Xe CCS/CAT fault, GPU reset, or fault messages during the test window. This is a successful reproduction-scale test of the previously failing prefill on `7.0.0-38`, although it does not prove the exact upstream commit is present or rule out intermittent failures. The package changelog does not list the flat-CCS fix. Further repeated testing is possible, but the formerly failing workload now completed once without the reported fault.
