## Architecture Notes
- `Esi.AI.PyTorch` owns Python training process integration, not UI state or SignalR contracts.
- `Esi.AI.Models` owns DTOs; Studio `DataService` orchestrates and `DataHub` delegates; client wrappers call the hub through `IDataService`.
- Training is a server-owned collection with pending publication before process start and subsequent updates/cancellation/removal reconciliation.
- A real XPU run is not considered verified by compiling the .NET solution; it requires a compatible PyTorch-XPU/BitsAndBytes environment and an actual supported Intel GPU.
- `TrainingRun` is a transient host-owned collection with one-active-run invariant; trained adapters are durable artifacts in a generated output directory.
- Security: reject non-loopback callers for process creation and use a fixed trainer script plus `ProcessStartInfo.ArgumentList`; validate dataset and bounded hyperparameters.
- Initial falsifiable hypothesis: the existing SignalR path can carry lifecycle updates without new HTTP surfaces; a focused process-manager test with a fake executable will disconfirm argument escaping, validation, or transition behavior before the page depends on it.
