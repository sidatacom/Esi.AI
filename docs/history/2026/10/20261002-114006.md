# Testprotokoll: Referenzmodell über alle Backends

## Benutzerauftrag

Alle verfügbaren Backend-Runtimes sollen dasselbe Referenzmodell laden und jeweils einen kurzen Chat-Test absolvieren. Jeden Schritt und jedes Ergebnis so festhalten, dass nach einer Unterbrechung genau beim nächsten nicht abgeschlossenen Backend fortgesetzt werden kann.

## Sicherheits- und Geltungsbereich

- Frühere Diagnose: wiederholter nativer OpenVINO-Segfault mit Qwen2.5-0.5B-Instruct-int4-ov; vollständiger PC-Freeze ist dadurch nicht abschließend erklärt.
- OOM ist durch die damals verfügbaren Messwerte nicht belegt. `systemd-oomd` war aktiv. Keine Host-, Kernel-, Treiber- oder Swappiness-Änderungen vornehmen.
- Modellläufe einzeln ausführen. Nach jedem Backend Ergebnis und Hostzustand prüfen und das Modell entladen, bevor das nächste Backend beginnt.
- Bei System-Freeze-Anzeichen, GPU-/Kernel-Reset, nativer Prozessbeendigung oder nicht mehr erreichbarem Studio keine weiteren Backendstarts; Ergebnis und letzten Zustand festhalten.
- Keine App-Konfiguration, Profile oder vorhandene Testdaten absichtlich verändern. Für Chats eine neue, eindeutig benannte Testsitzung nutzen, falls die UI dies erlaubt.
- Ein fehlgeschlagener Start oder Chat zählt als getestetes negatives Ergebnis. Keine stillen Wiederholungen.

### Flow-Router-Ursache und Fix

- Read-only-Abfrage der laufenden Studio-Datenbank vor dem Stop: `Chat request router | Version 1 | IsPublished=0`, `Tool calling router | Version 3 | IsPublished=0`, `Vision request router | Version 1 | IsPublished=0`.
- `Program.cs` ruft `FlowDefinition_SeedDefaultsAsync` beim Start auf. Der bisherige Seed übersprang jeden vorhandenen Namen, auch unveröffentlichte Einträge; `FlowRouteCoreAsync` suchte ausschließlich veröffentlichte Workflows. Damit blieb der Router nach dem Unpublish dauerhaft unauffindbar.
- Fix in `DataService`: Seed veröffentlicht vorhandene Default-Flows wieder (Versionsnummer wird erhöht). Wenn die angeforderte veröffentlichte Route zur Laufzeit fehlt, führt `FlowRouteCoreAsync` den Seed aus und liest danach erneut. Fehlende Defaults werden angelegt, unveröffentlichte Defaults werden repariert.
- Geänderte Regressionen: unveröffentlichter Default wird wieder veröffentlicht und geroutet; fehlender Default wird vor dem Routing angelegt, wobei alle drei Default-Router veröffentlicht sind.
- Validierung: `dotnet test src/Esi.AI/Esi.AI.Studio.Tests/Esi.AI.Studio.Tests.csproj --filter FullyQualifiedName~FlowRoutingServiceTests --configuration Debug --verbosity minimal -m:2 -p:RestoreDisableParallel=true -p:UseSharedCompilation=false` — 11/11 Tests bestanden. Build meldete 6 Warnungen, darunter 3 bestehende `NU1608`-Roslyn-Versionskonflikte.
- Die Anwendung wurde für den Test gestoppt; der Live-Datensatz ist bis zum nächsten Studio-Start weiterhin unveröffentlicht. Llama Vulkan war geladen, aber der Chat erreichte die Inferenz nicht.
- Nächster Schritt: Studio über EsiMCP starten, Live-DB auf `IsPublished=1` für alle drei Default-Router prüfen, dann den vorhandenen Llama-Vulkan-Chat einmal erneut senden.
