## Existing Evidence

- Earlier 118,052 prompt-token request completed with usage, one completion token, `finish_reason=stop`, and `[DONE]`.
- The repeat emitted only initial/null-content SSE chunks, with no token, usage, finish reason, or `[DONE]`; it was interrupted after 2:17.
- The live Xe watcher was empty, and a kernel-journal query for the repeat window returned no matching Xe errors.
- A separate 119,052 expected-token attempt had logged Xe `VM worker error: -105` (`ENOBUFS`), but that does not prove the repeat had the same failure.
- Initial code inspection shows `OpenVinoRuntime` starts synchronous native `GenerateWithHistory` on a long-running task. The generation API currently has no cancellation-token parameter.

## Findings

- The repeat's SSE timestamps convert to 2026-10-06 19:18:26 and 19:18:42 CEST. The kernel journal query from 19:00 through the end of that date returned no matching Xe errors, so the earlier 119,052 `-105` fault is not evidence for this repeat.
- The loaded configuration has no profile-specific timeout. Application settings use 120 base seconds plus 0.01 seconds per estimated prefill token; for about 118k estimated tokens, the deadline is roughly 1,300 seconds. The 2:17 interruption was well before that deadline and therefore was not a timeout failure.
- Confirmed cancellation defect: `OpenVinoChatSession.Generate` passes callbacks to both `LLMPipeline` and `VLMPipeline` that always return `StreamingStatus.Running`. The binding exposes `StreamingStatus.Cancel`, but the request cancellation token is not passed to this session. Thus cancellation during callback-driven generation is ignored.
- The observed stall occurred before any generated token, so the callback defect alone does not explain the long prefill. The synchronous native `GenerateWithHistory` call can continue running after the HTTP request is canceled; cleanup waits for that task before releasing the generation lock. This matches Studio continuing to consume CPU after the client was interrupted.
- The controller is designed to emit SSE heartbeats every 15 seconds while waiting, but the captured repeat had only one null-content frame after the initial role frame. The available capture does not explain why further heartbeats stopped.

## Conclusion

A code-level cancellation bug is confirmed and can leave native inference and its generation lock active after the client gives up. The underlying reason the 118k prefill stalled is not established: no matching Xe fault or native exception was captured for that repeat. The earlier 119,052 `ENOBUFS` failure remains adjacent evidence, not proof of this run's cause. Further root-cause attribution needs instrumentation around native call entry/exit, cancellation, and each SSE heartbeat during a controlled repeat.

## Cancellation Fix and Retest

- Added cancellation-aware callbacks to both OpenVINO chat-session implementations. They now return `StreamingStatus.Cancel` when the request token is canceled, use the streaming overload when cancellation is possible, and check cancellation after native generation returns.
- Propagated cancellation through `OpenVinoRuntime`, Core session callers, and the OpenAI middleware.
- Added a linked generation token in the SSE controller and cancel it when the stream exits before generation completes.
- The OpenVINO backend build succeeded. Studio rebuilt and started successfully through EsiMCP, and host readiness was confirmed.
- A real streamed request produced text deltas, then curl disconnected at 10 seconds (`curl` exit 28; 66,659 bytes received). Afterward `/v1/application/models` and `/v1/models` each timed out with zero bytes. `ss` showed the curl connection in `CLOSE-WAIT` on the Studio process. A separate follow-up request before the controller change also timed out without response.
- No Xe VM-worker, ENOMEM/ENOBUFS, CAT, or timed-out-job error appeared in the retest kernel window.
- Studio was stopped through EsiMCP; the active debug session is null and port 7010 is free.
