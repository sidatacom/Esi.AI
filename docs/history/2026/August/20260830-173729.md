# Session 20260830-173729

## User request
Why do `Models` and `LocalModels` both exist?

## Action plan
- Trace the `Model`/`LocalModel` contracts and their service consumers.
- Distinguish persisted application models from scanned local library models.
- Report whether both concepts are necessary and identify naming or design cleanup.

## Findings
- `LocalModel` is a transient filesystem-scan/library DTO. It is used by `/models`, downloads, compatibility metadata, and delete operations.
- `Model` is a persisted `Models` table record. It mirrors the scanned model fields and currently adds the persisted `ConfigurationId` used by `/backends`.
- `Model_UpdateAsync` synchronizes `LocalModel_ReadAsync()` results into `Models`; therefore `Model` is currently a derived persistence cache, not an independent model source.
- There is no separate `LocalModels` database table. `LocalModels` is only collection/property naming around the `LocalModel` DTO.

## Tracking
- [completed] Trace shared contracts and server services.
- [completed] Confirm UI responsibilities and persistence boundaries.
- [completed] Summarize the result and recommended cleanup.

## Summary
The split is understandable because local discovery and persisted configuration assignment are different concerns, but the current implementation duplicates the model identity fields. The design should either keep this split explicitly as scan DTO plus persisted registry, or consolidate on one canonical model entity and store compatibility/library metadata alongside its configuration assignment.
