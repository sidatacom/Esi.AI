## Summary
The provider and browser UI were not the root cause. Both paths reached the same OpenVINO runtime, where the active Qwen3.8 VLM could return native status `-17` after the process had entered an inconsistent model state.

## Findings
- A controlled reload in the existing process failed during `VLMPipeline.Create` with native status `-17` and left the projected model status marked as loaded with an error log.
- Restarting the supervised Studio debug session restored a clean native state.
- The same AWQ model then loaded successfully on `GPU.1`.
- A non-streaming text request returned HTTP 200 and `UI_OK`-equivalent model output.
- A real local PNG request returned HTTP 200 with non-empty VLM output.
- A streaming text request returned HTTP 200, normal SSE chunks, a stop chunk, and `data: [DONE]`.
- The `/chats` browser UI loaded the OpenVINO model and completed a SignalR chat exchange with `Backend: OpenVINO`, `Model: Qwen3`, and response `UI_OK`.
- No provider source, package version, generated bundle, or application source code was changed in this session.

## Conclusion
The reported provider and UI failures were downstream symptoms of the stale/inconsistent OpenVINO process state, not SSE parsing or SignalR transport failures. A controlled Studio restart is currently the verified recovery. The remaining engineering risk is the reload lifecycle: a failed `VLMPipeline.Create` can leave an old loaded-model projection and an unusable native state in the same process. A future focused change should make reload failure state explicit and prevent reuse of a potentially invalid pipeline.
